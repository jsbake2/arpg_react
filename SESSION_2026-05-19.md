## What changed today

### Movement-gated rules

New pair of conditions in the rule engine — `MOVEMENT_KEY_HELD` and
`MOVEMENT_KEY_NOT_HELD`. Lets the user add `NOT MOVING` to any rule
whose press would interrupt the character's movement (windups,
mobility skills, hard-casts). The engine waits until the user lets
go of W/A/S/D before firing.

Built per the locked design decisions in `MOVEMENT_GATE_HANDOFF.md`:
condition-based (composable with the other 9), WASD hardcoded (no UI
surface for the keylist), in-flight combo steps complete during
movement (only the initial press is gated), modifier-filtered
(Ctrl/Alt/Cmd+WASD doesn't count), fail-open on
Wayland-without-XWayland.

## How the feature surfaces in the UI

This caught the user out, so calling it out explicitly. There is **no
settings page** for configuring movement keys — that was a deliberate
design decision (WASD hardcoded). The feature appears as **two new
options in the per-rule conditions dropdown**:

1. Open the editor → **RULES** tab.
2. Pick a rule (or add one).
3. Click **+ ADD CONDITION**.
4. In the condition's **type** dropdown, scroll to the bottom — two
   new entries below `boss detected`:
   - `MOVING (W/A/S/D held)`
   - `NOT MOVING`
5. Pick `NOT MOVING`. No target / value fields appear (like
   `boss detected`).
6. Save.

The most common pattern is: add `NOT MOVING` to a rule whose skill
interrupts the user's character (mobility skill, hard-cast). The rule
then waits until the user releases W/A/S/D before firing.

If the user wants to change which keys count as "movement", edit
`MOVEMENT_KEYS` at the top of `arpg_react/watchers/movement_monitor.py`.
The handoff explicitly chose not to expose this as a profile field.

## How to verify it actually works in-game

Per the handoff's verification checklist:

1. Start the daemon: `arpg-react -v run --game d4`.
2. Watch the log for `movement monitor active: tracking ['a', 'd', 's', 'w']`.
   If you see `movement monitor disabled` instead, the listener
   failed to start — the gate will no-op (fail-open) but the feature
   won't actually do anything. Same failure mode as Alt+F9
   (pure-Wayland-without-XWayland kills both).
3. In the editor, add `NOT MOVING` to a rule that fires an
   interrupting skill.
4. Save, wait up to 60s for editor-sync to pull it (or restart the
   daemon).
5. In-game: hold W. Rule should NOT fire. Release W. Rule fires on
   the next tick where its other conditions are met.

## Notes for the next agent

- The handoff doc (`MOVEMENT_GATE_HANDOFF.md`) is still in the repo
  root. Keep it — it's the design contract for this feature and the
  best reference for "why it's like that" if anything needs to evolve.
- `MovementMonitor` is a real instance, not the `Callable` the engine
  accepts directly. Daemon passes `movement_monitor.is_moving` (the
  bound method) — same indirection pattern as `boss_detector`. Tests
  inject a `lambda: bool` instead of instantiating the real monitor.
- `EvalContext` is still a `@dataclass`, not a Pydantic BaseModel.
  Default `is_moving=False` keeps existing tests (and any external
  caller) from breaking.
