## What changed today

### 1. D4 loot filter format — fully decoded

User captured 5 export strings from D4's in-game loot filter
(empty / 1-rule / multi-condition / multi-rule with two recolors /
affix-rich) and saved them to `D4_FILTERS/`. All five decode cleanly
as **base64-encoded protobuf, no compression, no checksums**.

Schema lives in `D4_FILTER_SCHEMA.md`:
- `Filter { rules*, name, slot_id, ? }`
- `Rule { action, color (ARGB fixed32), conditions*, enabled }`
  - action: `0=Show`, `2=Recolor`, `3=Hide`
  - color: ARGB packed; `#FFD700` → `0xFFFFD700`, `#FF3030` → `0xFFFF3030`
- `Condition { type, ids*, amount, ip_max, ? }`
  - type 0 = Item Power (field 5 = upper bound)
  - type 1 = Rarity (field 4 = bitmask: 1=Common, 2=Magic, 8=Legendary)
  - type 4 = Greater Affixes (field 4 = count, field 6 = operator)
  - type 5 = Item Type (field 2 = ID, e.g. `0x6d14c`=Sword, `0x6d16e`=Helmet)
  - types 6 / 7 = Affix groups (one is "required all", other is
    "optional ≥N" — disambiguation deferred until generator built)

`tools/d4_filter_codec.py` — pure-stdlib protobuf encoder/decoder.
All 5 spike samples round-trip byte-identical, which means D4 will
accept anything we encode that conforms to the schema.

**Open work before the build-URL → loot-filter generator ships:**

### 2. Two launcher fixes for game-daemon mismatch

Symptom: pick POE2 in the launch dialog → panel shows POE2 tabs and
azurite theme, but BUILD tab fetches D4 builds. Two related bugs.

**Fix #1 (commit `4d76cd5`):** the launcher used to spawn the daemon
*before* showing the dialog, so the daemon always came up as D4.
Reordered: QApplication first → dialog → spawn daemon with
`--game <picked>` → panel reuses the same QApplication. Added
`run_panel_with_app(app, ...)` so launcher and standalone-panel
entry points share the panel boot path.

**Fix #2 (commit `7dd35a8`):** even with #1, an existing daemon left
over from a previous launch (or from a manual `arpg-react run`) would
still get attached to with the wrong game. Made it self-healing:
- Daemon writes its game to a marker file at
  `$XDG_RUNTIME_DIR/arpg_react/game` next to the IPC socket.
- Launcher reads the marker before deciding attach-vs-spawn. If the
  running daemon's game ≠ picked game, kill it (SIGTERM, fall back
  to SIGKILL after the standard shutdown grace period) and respawn
  with the right `--game`.

Helpers added in `launcher.py`: `_read_daemon_game(socket_path)`,
`_kill_running_daemon(socket_path)`.

Also (commit `1b4b723`, slightly earlier): the desktop launcher was
hardcoded to `--theme diablo`. Theme follows game now; the desktop
file's Exec line is just `arpg-react app`. `arpg-react install`
defaults to no theme override; `--theme` only baked in when user
explicitly opts in for the NEUTRAL dev palette.

## Late evening — bug-hunt round (2026-05-09 ~23:00)

User started the wizard build to play and surfaced three real bugs.
Two fixed, one diagnosed-only.

### A. Alt+F9 toggle "turns on but not off" — *diagnosed, not fixed*

`HotkeyController` (`arpg_react/hotkey.py`) registers the configured
combo with `pynput.keyboard.GlobalHotKeys` and the daemon flips
`engine.enabled` on each callback (`daemon.py:312-315`). Code path is
symmetric, so the bug is upstream in pynput.

Most likely cause: **modifier-state pollution.** Once monitoring is on,
`InputController` (`watchers/input_controller.py:135`) injects key
presses via `pynput.keyboard.Controller`. On X/XWayland those synthetic
events are visible to the *same-process* `GlobalHotKeys` listener and
corrupt its tracked-pressed-keys set, so subsequent `<alt>+<f9>`
combos fail to match. The original default (`config.py:241` → `"f9"`,
no modifier) wouldn't have hit this.

Suggested fixes (any of):
- Drop the modifier; use `<f9>` alone.
- Move the listener out-of-process (launcher hosts it, sends IPC
  command instead).
- Use a compositor/`xbindkeys` binding that POSTs `toggle_watchers`
  via the IPC socket directly.

Confirm before fixing: tail the daemon log, press Alt+F9 a second
time. If no `engine DISABLED` line appears, the listener silently
dropped it — that's modifier pollution. If it does appear, look
elsewhere.

### B. Bot typing letter "L" instead of clicking LMB — *fixed*

User noticed Tab/letter spam during play. Real cause: `L`/`R` D4
slots were resolving to the keyboard letters `l`/`r` instead of
mouse buttons.

Chain:

1. Editor's `_default_profile` (`editor/app.py:475`) seeded the D4
   keymap as `{s: s.lower() for s in slots}`, producing
   `{"L": "l", "R": "r"}`.
2. Daemon cached that to `~/.config/arpg_react/profile_d4.json` on
   first sync.
3. `daemon.py:355` merges cached profile *over* `DEFAULT_KEYMAP_BY_GAME`
   defaults — so the bad cache silently won, even though
   `config.py:83` has the correct `"L": "lmb", "R": "rmb"`.
4. `InputController._resolve` (`watchers/input_controller.py:74-79`)
   looks up `"l"` in `_MOUSE_TOKENS` (which only knows
   `"lmb"`/`"left"`/etc.), gets nothing, falls through to
   `("key", "l")` → pynput types L.

POE2 dodged this because its slots are `["LMB", "MMB", "RMB", ...]`,
which lowercase to `"lmb"`/`"mmb"`/`"rmb"` — those *are* in
`_MOUSE_TOKENS`. The single-letter D4 slots fell into the gap.

**Fix**:
- `editor/app.py:_default_profile` — added `_mouse_slot_overrides`
  so D4 `L`→`lmb`, `R`→`rmb`. Rsync'd to `10.0.0.16`,
  `d4-rule-editor.service` restarted (active).
- `~/.config/arpg_react/profile_d4.json` — patched in place from
  `"l"`/`"r"` to `"lmb"`/`"rmb"`.
- Editor DB has no saved keymap row (`data.db` is 0 bytes), so no
  DB row will overwrite the fix on next sync.

Verified live in production log: `23:24:59 input keymap updated:
{'L': 'lmb', 'R': 'rmb', ...}` and `23:25:03 press L → mouse:left`.

### C. Boss rule never fires — *root cause confirmed, fix not applied*

User's wizard build has a `BOSS_DETECTED` rule targeting LMB with
5s cooldown. In a real boss fight (Helltide Blood Maiden), the diag
log shows `BOSS_DETECTED✗` on every 3-second tick across the entire
encounter — the rule fired exactly once at `23:25:03` (one-frame
false positive), then nothing.

**Root cause**: `BOSS_REF` (`watchers/detector_refs.py:81`) is a
22×23 patch at `(1272, 84, 1294, 107)`, captured 2026-05-06 against
"SATHIA FLESHRIPPER" in `arpg_stuff/d4/boss_hp_bar.png`. That bbox
sits *under the boss-name text*, not on the bar's invariant chrome.
80% match / 30 RGB tolerance is essentially "this exact letter
glyph pattern" — any other boss name and the template misses.

**Two fix paths** (deferred):
- *Quick*: recapture the template against the bar's left endcap
  (the dark horn/socket UI shape) which is identical across every
  boss. Re-encode `_BOSS_B64`. Brittle if Blizzard repaints the UI
  but ships tonight.
- *Proper*: replace template-match with feature-based detection —
  scan a horizontal strip at y≈85-90 across x≈900..1620 for the
  red-gradient HP bar pattern (high R, low G/B, sufficient run-length).
  Survives any boss, locale, or minor UI tweak.
